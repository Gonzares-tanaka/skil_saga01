## 1. QUEST管理構造

[rpg/exploration.py](../rpg/exploration.py)の既存`Exploration`が1件だけ管理します。種別は`explore / investigate / hunt`、Lvは1～3です。9個の別システムにはせず、受注・配置・進捗・帰還・報酬を共通化しました。定義と安全な候補抽出、画像座標は[rpg/quests.py](../rpg/quests.py)へ分離しています。

## 2. active_questのデータ構造

未受注は`None`、受注中はJSON化できる辞書です。座標はリスト、階はB1F=1です。

```json
{
  "type": "investigate",
  "level": 2,
  "id": 2,
  "target_floor": 8,
  "points": [[2, 5], [12, 20], [20, 10]],
  "investigated_points": [[2, 5]],
  "progress": 1,
  "required_count": 3,
  "completed": false,
  "reward": 5
}
```

`id`は既存DEBUG・検証コードとの互換用Lvです。QUESTの種別は`type`で区別し、`id`だけで別種の依頼を識別しません。討伐には`hunt_enemy_id`と`hunt_source_floor`も入ります。`completed`は目的達成・安全帰還待ちを表し、報酬受取後は辞書全体を`None`にします。

## 3. 同時1件制限の実装方法

`accept()`は最初に`active_quest`を検査し、存在すれば生成前に拒否します。受注中のAで対象地点・進捗・乱数状態が変わらないことを確認しました。PUBのQUEST画面には受注中の依頼を表示します。メッセージは`data/quests.json → messages.already_active`で編集できます。

## 4. 探索QUEST処理

対象階の安全な既存候補から1地点を選択し、人影を重ね描画します。接触またはAで発見し、`progress=1 / completed=True`になります。目的達成時のTRZ支給はありません。徒歩・RETURNで生還すると報酬を確定TRZへ加算します。

## 5. 調査QUEST処理

同じ対象階から重複しない複数地点を抽出し、虫眼鏡を表示します。調べた座標を`investigated_points`へ追加し、同じ地点を再度調べても進捗は増えません。全地点を調べると帰還待ちになります。PUBでは`1 / 3`などの進捗を表示します。

途中の安全帰還では進捗・受注を保持し、全滅時は調査済み座標・進捗・目的達成をリセットします。対象階・地点・受注は保持し、同じ依頼へ再挑戦できます。

## 6. 討伐QUEST処理

魔物の顔へ接触すると`battle_kind='quest_hunt'`の1体戦へ進みます。対象階の通常敵データを使い、B5/B10/B15では同じエリアの直前の通常階の敵候補を使います。元の敵データは変更せず、生成した討伐用コピーにだけ補正します。

初期値は通常の階層倍率に対しHP×1.25、STR+1、DEF+1。AGI・魔法比率などは通常敵の値です。通常戦闘のSKILL/ITEM/GUARD/RUN、成長・閃き・Uses消費を利用します。ボス扱いにはせず、守護者・デーモン・階層解放フラグを更新しません。

勝利リザルト後に目的達成、TRZ報酬は安全帰還時だけです。現在の通常戦闘にはTRZ支給がないため、戦闘TRZとの二重取りもありません。RUN・DRAWでは対象が残り、再接触またはAで再戦できます。全滅は通常の拠点帰還・未確定TRZ喪失処理を使います。
