# QUEST依頼人・フレーバー 実装／検証報告

Skill Seekers!!~深淵のアムリタ~ / 2026-10-07

QUESTのLv→種別選択に続いて、依頼文を読んで「受注する／受注しない」を選ぶ確認画面を追加しました。依頼人と短い依頼文、報酬・配置・進行条件は維持しています。

受注確認の追試では、全9組で明示的な辞退・Bでの辞退・表示した依頼の受注を確認しました。辞退時は受注も進捗も作らず、TRZ・ゲーム本体の乱数・前回受注したIDを変更しません。確認中の文章と対象階・報酬は、受注時に再生成せずそのまま引き継ぎます。長文は最後のページへ進んでから判断し、途中のAでは受注しません。

## 1. QUEST_FLAVOR_TEXTS相当の場所

[data/quest_flavors.json](../data/quest_flavors.json)の`texts`です。種別キーは`explore / investigate / hunt`、Lvキーは文字列の`"1" / "2" / "3"`です。`fallbacks`には同じ種別・Lv別の汎用文があります。読み込みとデータ検査は[rpg/quests.py](../rpg/quests.py)の`load_quest_flavors()`です。文章は描画・更新・受注処理に埋め込んでいません。

## 2. フレーバーデータ構造

```json
{
  "id": "investigate_l2_01",
  "requester": "歴史研究者",
  "lines": [
    "この地下には古代の水脈が",
    "残っているらしい。",
    "各所の痕跡を調べてくれ。"
  ]
}
```

候補を追加する場合は該当する種別・Lvの配列へこの形式で追加してください。`id`はファイル全体で重複不可です。保存済み依頼との対応を保つため、既存IDはなるべく維持してください。空の候補配列でも、その種別・Lvの汎用文を使用します。

## 3. 初期フレーバー数

ランダム候補27件＋汎用文9件です。各候補は2～3行、初期候補27件すべてが自動折り返し後も3行以内に収まることを実描画で確認しました。

## 4. 探索Lv1～3の文章数

Lv1：3、Lv2：3、Lv3：3、合計9件です。日常の行方不明者・落とし物から、不穏な調査隊や深層の古い痕跡へ変化します。人・物・痕跡のいずれにも矛盾しないよう、発見時の表示だけを「依頼の手がかりを見つけた。」へ変更しました。追加の物品取得や救出処理はありません。

## 5. 調査Lv1～3の文章数

Lv1：3、Lv2：3、Lv3：3、合計9件です。地下水・石・植物、古代水脈・魔力・建造物、歴史の記録や紋様を扱います。複数地点を調べる既存の目的に合わせています。

## 6. 討伐Lv1～3の文章数

Lv1：3、Lv2：3、Lv3：3、合計9件です。商人や新人への被害、調査隊を襲う個体、深層の帰路を脅かす魔物を扱います。本編の守護者・デーモン・ロードオブエリシオンとは競合せず、アムリタの真相を確定する文章もありません。

## 7. requesterの管理方法

各候補と汎用文の`requester`を表示します。冒険者・商人・歴史研究者・学者・魔術研究者・薬師・鉱夫・旅人・城下町の衛兵・住人・酒場の主人など、立場で表現しています。依頼人の変更はJSON編集だけで可能です。

## 8. flavor_idの管理方法

`Exploration.preview_quest()`で既存の階・地点・討伐敵と対応する種別・Lvの文章候補を生成し、確認中の依頼を保持します。対象生成はゲーム本体の乱数のコピーで行い、受注時にだけ生成後の乱数状態を反映します。文章用の`flavor_rng`も独立しており、ゲーム本体の乱数を追加消費しません。文章選択の有無で対象階・地点・討伐敵・本体の乱数状態が一致することを全9組で確認しました。既存DEBUG向けの`accept()`直接受注も維持しています。

表示時は`Exploration.quest_flavor()`が現在の種別・Lvのプール内だけでIDを解決します。IDが不明・削除済み・別種別・未設定の場合は対応する汎用文を返します。表示時の再抽選や、保存されたIDの書き換えはありません。

## 9. active_questへ追加した項目

`flavor_id`だけです。文章配列・依頼人は保存しません。既存の種別・Lv・階・座標・進捗・報酬・討伐敵情報は維持しています。JSON往復、全滅時の進捗リセット、最終戦チェックポイントからの3回復元でも同じ依頼文を取得できました。

受注前だけの`pending_quest`と生成後の乱数状態は一時データであり、辞退・受注確定・NEW GAMEで破棄します。SAVE対象の`active_quest`とは分けています。

## 10. 将来SAVEするべきQUEST項目

`active_quest`を丸ごとJSON保存する方針です。具体的には`type / level / id / target_floor / points / investigated_points / progress / required_count / completed / reward / flavor_id`、討伐ではさらに`hunt_enemy_id / hunt_source_floor`です。未受注は`null`です。

文章と依頼人は読み込み後に`flavor_id`から取得します。連続回避をLOAD前後でも継続したければ`last_flavor_id`も別途保存できますが、同じ依頼文の復元には不要です。SAVE/LOAD自体は追加していません。

## 11. QUEST BOARDのレイアウト変更

160×120・既存の色番号0～3を使用します。

| 内容 | Y座標 |
|---|---|
| QUEST BOARD / 依頼 | 既存の上部帯 |
| 種別・Lv | 15 |
| 依頼文・最大3行 | 28・37・46 |
| 依頼人 | 58 |
| 対象階・進捗／必要数 | 71 |
| 報酬TRZ | 83 |
| 安全帰還条件／達成状態 | 98 |
| 操作案内・一時通知 | 112 |

受注前のLv選択・種別選択に続いて`quest_preview`で依頼を確認します。上記の依頼文・依頼人・対象・報酬を共用し、報酬行に安全帰還条件を表示、Y=94・103に「受注する／受注しない」を上下配置します。上下で選択、Aで決定、Bも辞退です。長文は最終ページに選択肢を表示します。

受注中はBでPUBへ戻り、長文のときだけAで依頼文を読み進められます。新規受注はできません。受注確認・初期文章・長文・達成状態の画像を目視確認し、文字や他の情報との重なりはありません。

## 12. 長文はみ出し対策

既存の日本語フォントの実ピクセル幅で折り返します。`QUEST_FLAVOR_MAX_CHARS=36`は既存UIの4px単位で144px、`QUEST_FLAVOR_LINE_HEIGHT=9`、`QUEST_FLAVOR_LINES_PER_PAGE=3`です。定数は`rpg/quests.py`にあります。

3行を超えた部分はAで次ページへ進み、最後から最初へ戻ります。空行とデータ内の改行も維持します。各ページで依頼人・対象・進捗・報酬・帰還条件を固定表示し、ページ送りで受注データや乱数を変更しません。依頼人名が枠を超える場合は既存のピクセル幅による`~`省略を使います。

## 13. 同じ文章の連続防止方法

前回受注した1件のIDだけを`Exploration.last_flavor_id`に保持し、次の候補から除外します。辞退では前回受注IDを更新しません。候補が1件しかない場合はその候補を使用し、0件なら汎用文を使用します。履歴一覧や複雑な管理は追加していません。NEW GAMEでは新しいExplorationとともに初期化されます。

## 14. 既存QUESTロジックを維持したこと

Lv1～3の対象帯、B5F/B10Fボスによる解放、Lv→種別の選択受注、同時1件、対象候補とシンボル、調査地点数、討伐性能、報酬額、RETURN、安全帰還、全滅時の進捗リセットを維持しています。初期TRZ 3/0も維持しています。

[変更範囲の確認](quest_flavor_preservation.json)：開始時点の本体・データ・リソース46ファイルのうち42ファイルはバイト単位で同一です。変更した既存ファイルは`rpg/quests.py / rpg/exploration.py / rpg/dungeon_app.py`と、探索の発見メッセージ1行だけを変更した`data/quests.json`です。マップ・画像・パレット・音声・敵データ・成長・技性能・アイテム価格・最終戦処理は変更していません。

## 16. 既知の問題・制限

- 実ブラウザ・スマートフォン実機の表示とタッチ入力は未確認です。
- 人間が長文へ編集した場合は複数ページになります。初期27文はすべて1ページです。
- データを編集して同じIDの文章を書き換えた場合、既存の受注にも編集後の文章を表示します。削除したIDでは汎用文になります。
- SAVE/LOADは未実装です。今回の永続性確認はJSON往復と既存の最終戦チェックポイントによる復元です。
